# OpenAPI strategy

## Status
Decided.

## Context

The MVP exposes three HTTP endpoints with strict contracts (status codes, body shapes, headers — see `api-contract.md`). We want a machine-readable specification that:

- Documents the API for human consumers (`/docs` page).
- Drives type-safe Go server stubs so the handler signatures cannot drift from the spec without a compile error.
- Serves as a stable artifact for client SDKs if anyone needs them later.

Three common approaches in the Go ecosystem:

| Approach | Source of truth | Tooling | Drift risk |
|---|---|---|---|
| **Spec-first** | hand-written `openapi.yaml` | `oapi-codegen` generates Go interfaces | low (compiler enforces match) |
| **Code-first** | annotations on handlers | `swaggo/swag` generates yaml | medium (annotations and code can disagree) |
| **Manual** | hand-written yaml + hand-written handlers | none | high (only tests catch drift) |

## Decision

**Spec-first with `oapi-codegen`**. We write `api/openapi.yaml` by hand and generate Go handler interfaces and request/response types from it. The yaml is the single source of truth for the contract.

## Why

- **No drift between docs and code.** `oapi-codegen` produces a Go interface that the implementation must satisfy. Adding or changing a field in the yaml without updating the handler is a compile error. With AI-generated code, the compiler is the main objective judge of consistency between intent (yaml) and implementation (Go).
- **Structural defense against hallucinations.** An AI agent cannot invent a field in the Go types — they are generated from yaml. To add anything to the contract, the agent must edit the yaml explicitly, and that edit is visible in the PR diff.
- **Yaml is the human review surface.** Reviewing every line of an AI-written PR is impractical. Reviewing the yaml diff is fast and catches contract changes precisely. Everything that follows from the contract (request and response types, the `/docs` page) is derived automatically.
- **TDD-friendly.** Generated types are used directly in handler tests. Tests reference the same types as production code, so contract changes show up in test failures, not silent misbehavior.
- **No annotation noise in handlers.** Handler files stay focused on behavior. Less load-bearing in an AI workflow than for humans, but still useful when reading a specific handler file.
- **Standard tool, low ceremony.** `oapi-codegen` is the de-facto choice in the Go community; integration with `chi`, `echo`, or stdlib `net/http` is one config line.

## Workflow

1. Edit `api/openapi.yaml`.
2. Run `make generate` (which calls `oapi-codegen`). It regenerates `internal/api/oapi_gen.go` with:
   - Handler interface (`ServerInterface`).
   - Request and response Go structs.
   - Optional client code (we will skip it in MVP).
3. The handler implementation must satisfy `ServerInterface`. If the yaml changed and the handler did not, the build fails.
4. Run tests. Generated types are imported into handler tests so spec changes propagate.

`go generate` is wired via a directive in a single file (e.g. `internal/api/generate.go`):

```go
//go:generate go tool oapi-codegen -config ../../api/oapi-codegen.yaml ../../api/openapi.yaml
```

The `oapi-codegen` binary is pinned in `go.mod` via the Go 1.24+ `tool` directive (same pattern as `golang-migrate` — see `conventions.md`). This keeps a single tool-pinning style across the repo and ensures transitive dependencies of the codegen tool are recorded in `go.sum`.

`make generate` wraps this for humans and agents alike.

## File layout

```
api/
  openapi.yaml           # source of truth
  oapi-codegen.yaml      # codegen config (package name, output mode)
internal/
  api/
    generate.go          # contains the //go:generate directive
    oapi_gen.go          # generated; checked in
    server.go            # implements ServerInterface
    server_test.go       # handler tests
```

The generated file is **checked in**. This avoids surprises in CI environments without the codegen tool installed and makes diffs visible in PR review.

## Hosting `/docs`

The service exposes the spec and a Swagger UI at:

- `GET /openapi.json` — the raw spec (the JSON form embedded by `oapi-codegen`'s `embedded-spec: true`; served via `api.GetSpecJSON()`).
- `GET /docs/` — Swagger UI (also embedded; we vendor the static assets from `swagger-api/swagger-ui`).

Both are unauthenticated. They expose only public contract information — no secrets — and are useful for any internal consumer.

## AI agent workflow

Code is written by AI agents and reviewed by humans. The OpenAPI setup is calibrated for that.

### Generated files are off-limits

`oapi_gen.go` carries a `// Code generated by oapi-codegen. DO NOT EDIT.` header. Agents must not modify it. To change the API surface, edit `api/openapi.yaml` and run `make generate`.

The agent's instructions repeat this rule. The CI gate below enforces it as a fallback.

### `make check` before every commit

`make check` is the single command an agent runs before committing:

```
make check:
    go generate ./...
    git diff --exit-code        # fails if generated files were not committed
    go test ./...
    golangci-lint run
```

Each step blocks the commit on failure. The human reviewer trusts that `make check` passed; without it, every PR review would have to re-run the chain manually.

### CI gate is the primary defense

CI runs the same `make check` and fails the PR on any error. This is **not** a nice-to-have catch-net for "forgot to regenerate" — it is the **primary** mechanism that prevents AI-generated code from drifting away from the spec.

The most important step in the chain for spec consistency is `git diff --exit-code` after `go generate`. It catches:
- The agent edited yaml but skipped regeneration.
- The agent edited the generated file directly (in violation of the rule above).
- The codegen tool version changed and produced different output.

Any of these would otherwise ship inconsistencies into a release.

### Yaml is the diff that humans review

Human PR review focuses on `api/openapi.yaml` and the handler implementation. Generated `oapi_gen.go` diffs are large and follow mechanically from the yaml; humans skim them at most. This is why the yaml has to be the source of truth — not the convention, but the actual decision point.

## Versioning

For MVP: no version prefix in URLs. The spec carries a single `info.version` field, updated when the contract changes in a breaking way. Breaking changes in MVP scope are unlikely; if they appear, the next iteration will define a versioning policy (URL prefix vs `Accept` header).

## Validation

The MVP **enables runtime validation in dev and test** environments using `kin-openapi`'s validator middleware. Production stays opt-in for now.

### Why we now run runtime validation

The compiler enforces type structure: the handler signatures match the yaml. But the compiler does not catch semantic drift inside the body of the handler. An agent-written handler can compile and still:

- Return a response with a missing required field (if the type uses `omitempty` or a pointer that ends up nil).
- Return an enum value that is not in the allowed set.
- Branch into a status code that the spec does not declare.
- Forget to validate a request payload that the spec marks as constrained.

These are exactly the kind of plausible-looking-but-spec-violating errors LLM-generated code produces. Runtime validation against the loaded spec catches them on the first failing test.

In a hand-written codebase, this defence is "nice to have". In an AI-written codebase, it is a primary safety net — the same role the compiler plays for type structure, extended to runtime semantics.

### How it is wired

The middleware is added in dev/test profiles only:

```go
if cfg.Env != "production" {
    router.Use(openapi3filter.Middleware(loader.LoadFromBytes(specBytes)))
}
```

Behind a config flag so it can be enabled in production later. The library is `github.com/getkin/kin-openapi`; well-maintained, no exotic dependencies.

### Why production is opt-in

If the validator runs in production and the live spec lags behind a hotfix in the handler, real traffic would fail at the validator. Until the deploy pipeline guarantees yaml-and-code shipped together (which our `make check` already does for PRs), keeping production strict can cause an outage during a roll-out window. We turn it on once that confidence is built.

The longer-term goal is "production-on by default" — the protection it offers is too valuable to remain test-only forever.

## Not in scope here

- **Generated client code.** `oapi-codegen` can also generate clients; we skip that until a Go consumer asks for it.
- **Production-on runtime validation by default.** Goal, not MVP — see "Validation" above.
- **Multi-spec setups** (separate specs for public vs internal API). The service has one API surface in MVP.
- **Webhook callbacks specs.** None in MVP.
